# Architecture Memlog — Threadline Distributed Commerce Platform
Scope: Multi-tenant, event-driven fashion e-commerce backend in Golang
Purpose: Build Substrate for Go microservices & Technical Portfolio for GFG SE II / Senior roles
Altitude: Initiative / Platform Spine
Status: Active (Coaching Path)

## Entries
- event: workspace initialized for Threadline Architecture Spine
- constraint: implementation strictly in Golang 1.23+
- constraint: target 6 right-sized microservices + 1 API gateway
- constraint: 0 oversell invariant during high-concurrency flash sales (10k concurrent requests)
- constraint: distributed order orchestration via Saga
- constraint: multi-tenancy enforced at database layer (PostgreSQL RLS)
- constraint: outbox pattern with CDC for reliable event publishing
- decision: AD-1 [ADOPTED] Multi-module Monorepo with Go Workspaces (go.work)
  - binds: repository layout, CI pipelines, Docker builds, pkg/ shared modules
  - prevents: dependency coupling across services and bloated container images
  - rule: each service and pkg/ maintains its own go.mod; local dev uses go.work; CI verifies builds per service using paths-filter.
- decision: AD-2 [ADOPTED] Scheduled / Pre-warmed Hot SKU Sharding for Flash Sales
  - binds: inventory-service, catalog-service, admin campaign management
  - prevents: runtime split-brain and reconciliation race conditions caused by adaptive in-flight stock migration
  - rule: flash-sale SKUs must be explicitly configured and pre-warmed into Redis sharded counters before event start; dynamic mid-flight migration is forbidden.
- decision: AD-3 [ADOPTED] Saga Pivot Transaction & Retry-Forward-Only Guarantee
  - binds: order-service, inventory-service, payment-service
  - prevents: dual charge / partial refund inconsistencies and customer balance discrepancies
  - rule: once payment capture succeeds, the Saga transitions to Retry-Forward-Only; compensation (refund) is prohibited at this stage; unrecoverable step failures divert to DLQ and page On-Call.
- decision: AD-4 [ADOPTED] PostgreSQL Multi-Tenant RLS & Fail-Closed Session Scope
  - binds: all services using PostgreSQL, background workers
  - prevents: cross-tenant data leakage via connection pool session pollution
  - rule: all tenant queries must run inside an explicit transaction with SET LOCAL app.tenant_id = $1; default behavior without context is fail-closed (0 rows); background workers must NOT have BYPASSRLS and must iterate tenants sequentially with explicit SET LOCAL.
- decision: AD-5 [ADOPTED] Entity-Scoped Kafka Partition Key Strategy
  - binds: outbox publishers, event schemas, Kafka topics
  - prevents: hot-partition skew from imbalanced tenant volumes while preserving strict per-entity causal ordering
  - rule: Kafka messages must be keyed by entity ID (order_id, sku, reservation_id); keying by tenant_id is strictly forbidden.
- decision: AD-6 [ADOPTED] Logical Database-per-Service Isolation with Enforced Role Boundaries
  - binds: database provisioning, migrations, service connection credentials
  - prevents: accidental cross-service SQL JOINs and coupling while maintaining fast local bootstrap
  - rule: each microservice owns an isolated logical database with a dedicated DB user; cross-database grants are strictly blocked at PostgreSQL permission level; single Postgres cluster used in local dev.
- decision: AD-7 [ADOPTED] Zero Remote I/O Inside Database Transactions
  - binds: all application services, database repositories, transaction management
  - prevents: connection pool exhaustion, cascading lock freezes, and transaction timeouts during downstream degradation
  - rule: executing remote network calls (HTTP, gRPC, Redis, Kafka) inside an open PostgreSQL transaction is strictly prohibited. Database transactions must complete within microseconds.
- decision: AD-8 [ADOPTED] Strict Idempotency with Request Hashing & In-Flight Mutex
  - binds: API Gateway, order checkout, payment capture/refund, webhook ingestion
  - prevents: duplicate charges, duplicate order creation, and race-induced double fulfillment
  - rule: mutation requests requiring idempotency must supply an Idempotency-Key header; identical key with differing SHA-256 payload hash yields 422 Unprocessable Entity; concurrent in-flight requests yield 409 Conflict.
- decision: AD-9 [ADOPTED] End-to-End W3C Trace Context Propagation Across Kafka
  - binds: HTTP gateway, gRPC interceptors, Outbox table schema, Kafka producers & consumers
  - prevents: broken trace spans across asynchronous message boundaries
  - rule: all services must propagate W3C traceparent headers; outbox events must persist traceparent in a JSONB headers column; publishers must inject traceparent into Kafka record headers; consumers must extract and resume span.
